# ArchiveManagement

存档管理工具 —— 用于分支、备份、恢复和导出游戏存档的桌面工具.

## 开发

要求：Python >= 3.12 与 [uv](https://docs.astral.sh/uv/).

```shell
uv sync --locked          # 只安装依赖（含 dev 组）,不安装当前项目
uv run python -m archive_management init --root .\dev-data   # 初始化目录/配置/数据库
uv run python -m archive_management doctor --root .\dev-data # 健康检查
uv run pre-commit install # 安装 Git 提交钩子
```

### 启动UI
```shell
uv run python -m archive_management gui --root .\dev-data # 启动图形界面(基于本地 SQLite, 首次为空库)
uv run python -m archive_management gui --smoke 1         # GUI 冒烟自检(自动关闭)
```

GUI 使用本地 SQLite 作为数据源(阶段 C): 首次进入为空库, 通过左侧"+ 添加游戏"录入游戏, 再在"游戏设置"中为该游戏手动添加/编辑/删除"原始存档位置"(支持选择目录或文件, 记录规范化绝对路径并对可用性与重复做校验); 应用自动管理的备份目录与原始位置分开展示, 避免误操作.演示后端仅保留给离线开发与冒烟测试使用.

备份能力(阶段 D):

- "立即创建备份"(或全局快捷键 `Ctrl+Alt+S`)把当前存档位置复制为应用自有存储中的一次快照: 先写入同级的临时目录, 逐文件计算 SHA-256 并复核, 全部成功后才原子改名为正式快照; 目标已存在时直接失败, 绝不覆盖已有备份, 失败或取消不会留下半成品节点。
- 每次备份(手动/分支/自动)之前都会先与**当前节点**做内容比对: 存档一点没变时不会产生新的备份。手动点击时弹窗告知"存档没有变化", 自动备份则静默跳过(只在日志里留 DEBUG 记录), 恢复前的安全点同理跳过。
- 备份根目录下用**游戏名称**而不是数字 id 分目录: 目录名为 `<游戏名称>-<短哈希>`, 例如 `OuterWilds-3f9a2c1b`。名称部分由识别到的游戏名称规范化而来(保留中文, 替换文件系统非法字符), 短哈希由"名称 + 全部存档路径"推导, 用来区分同名游戏。目录名在首次备份时确定并记录在数据库中(见 `games.storage_key`), 之后改名或增删存档位置都不会搬动已有备份。
- 录入时的原始名称单独保留(`games.original_name`), 改过名后概要区会额外显示"原始名称"与"备份目录", 方便在磁盘上对照找到对应目录。
- 旧的数字目录(如 `3/20260913T051821-93dfe366`)不会被搬迁或删除: 每个备份节点都记录自己的相对路径, 因此历史备份照常可以校验、恢复与删除, 只有新备份才会写入带名称的新目录。
- "恢复到此节点"把选中的备份写回原始存档位置, 并把**当前节点**切换过去(带 ● 标记), 之后的"向下保存"与"创建分支"都从该节点重新开始. 恢复前会深度校验快照清单、检查目标路径是否可写(盘符根目录、用户主目录、应用备份目录一律拒绝)并探测游戏进程; 检测到游戏在运行时会提示风险并要求明确确认.
- "从此处创建分支"以选中节点为父节点并记录分支名(默认文案为本地化的"分支"/`Branch`, 英文环境自动用英文); "重命名 / 描述"可修改备份名称与最多 200 字的描述.
- "删除备份"按分支树决定处理方式: 同一线路上的节点被删除时后续节点自动上移; 删除分支根节点会先提示将连带删除其分支下的全部备份, 用户确认后整棵树一并删除.
- 新建的手动备份带默认名称"手动备份"(自动备份为"自动备份")直接显示在标题列, **内容摘要默认为空**, 需要说明时再用"重命名 / 描述"补充。
- 默认展示"分支树"(按层级缩进, 自动备份只显示最新一份), 可切到"时间线"查看全部备份及其所属分支.
- 定时备份**按游戏独立配置**(周期如 `30m` / `2h` / `1d` 与自动备份保留份数, 默认 3 份): 主入口是"游戏设置 → 定时备份", 工作区的"定时任务"用于统一查看与管理。周期留空即取消; 自动备份超出保留份数时最旧的一份连同快照被清理, 且不会让后续节点变成孤儿.
- 定时任务在应用重启后会自动从数据库恢复(周期、启用状态与保留份数都不会丢); 每次执行后会重新读取后端排出的**下次运行时间**, 即使本次因"存档未变化"被跳过, 界面上的下次运行与概要卡也会刷新。
- **未配置存档位置的游戏无法创建定时任务**(没有可备份的内容): 新增前就会拦下并提示原因, 后端也会再校验一次。
- 右侧的"任务状态"卡展示当前操作进度、下次运行时间、备份目标与快捷键(长文案自动换行); 定时配置入口在"游戏设置"与工作区的"定时任务"。
- 工作区的"定时任务"打开全局任务窗口: **只列出已配置定时备份的游戏**, 每条标明来自哪个游戏、下次运行时间、当前设置的周期与已保留的自动备份份数, 并可编辑、暂停/继续与删除; "新增任务"先弹出可**输入关键字筛选**的游戏选择框(弹窗里注明推荐去单个游戏的编辑区配置)。
- 顶栏只保留品牌与导出按钮: 不再显示"上次同步"时间与主题切换按钮——**主题切换在"工作区 → 设置"**里, 设置窗口不再包含定时任务相关信息; 工作区入口为"游戏发现"、"定时任务"与"设置", 三个入口共用同一个窗口位置: **重复点击同一个入口只会把已打开的窗口提到前台**, 再点其他入口会提示先关闭当前窗口, 因此不会同时开出多个配置窗口(关掉后即可打开另一个)。
- 左侧状态卡显示备份存储的**当前占用**(不再显示磁盘剩余与快捷键), 并在每次数据变化后刷新。
- 每个备份节点都记录内容哈希与文件清单, 列表中的"已验证"标记来自快照清单的实际校验.

恢复能力(阶段 E):

- 恢复对话框在**同一个窗口**内展示快照规模、写回目标与风险提示, 并可勾选"恢复前先创建安全点"(默认勾选, 便于回到恢复前的状态).
- 写回过程先在目标同级的 `.restore-*` 暂存目录里重建内容(逐文件核对哈希), 再用改名原子替换; 替换失败会把原内容改名回滚。存档里被删掉的文件与目录会被重新建出来。
- 快照之外的文件在恢复后原样保留(恢复是"覆盖"而不是"镜像"): 需要回到恢复前的状态时, 从时间线恢复"恢复前安全点"即可——安全点是恢复操作的可逆手段, 因此不再需要隔离区。
- 快照的清单路径按不可信输入处理: 绝对路径与 `..` 越界条目直接拒绝; 符号链接只重建链接本身, 环境不允许时记为跳过项而不是中断恢复。
- "恢复前安全点"标记为 `is_safety` 的备份**只出现在时间线视图**, 不占用分支树的层级位置; 用工具栏的来源筛选选择"恢复前安全点"可以单独查看它们。
- "删除原始存档位置"把磁盘上的原始目录移入**系统回收站**(绝不永久删除), 删除前要求输入游戏名称确认, 并显示目标路径、文件数量与总体积; 盘符根目录、用户主目录与备份目录会被拒绝。

操作日志(阶段 E):

- 所有用户操作都写入日志目录下的 `archive-management.log`(**不落数据库**): 备份/分支/恢复/删除等高风险操作用 INFO, 主题切换、视图切换、筛选、选中这类基础操作用 DEBUG。
- 默认控制台只打印 INFO 及以上的高风险操作; 加 `--verbose`(或 `gui --verbose`)可以在控制台看到全部基础操作。
- 日志采用滚动文件(单文件 1 MB, 保留 5 份), 并且不记录 API Key、凭据、文件内容或完整敏感路径: 路径字段统一用 `redacted_path()` 脱敏为"父目录名/条目名"。

本地游戏发现(阶段 E-1):

- 工作区的"游戏发现"打开探测窗口, 窗口分为"探测结果"与"监控目录"两个页签(**默认停在探测结果**): 探测结果页扫描 Steam(库清单 `libraryfolders.vdf` + `appmanifest_*.acf`)、Epic(启动器 `*.item` 清单)、GOG 与 Battle.net(注册表安装路径)以及监控目录, 把发现的游戏列为待确认的候选。
- 探测结果**不会自动进入游戏库**: 只有点"导入为游戏"才会新建游戏记录(探测到的是安装目录而不是存档目录, 因此不会自动登记成存档位置); 也可以"忽略"(之后扫描不再提示, 可随时恢复)或"修正路径"。列表**默认只看"待处理"**(这个页面的用途就是把发现的游戏收进游戏库), 可切换全部/已导入/已忽略; 筛不到内容时给出的是该筛选下的空状态与各状态数量, 而不是笼统的"暂无探测结果"。
- 监控目录页用于覆盖平台客户端未安装、未登录或路径自定义的情况: 目录下的每个子文件夹都当作候选游戏(目录里没有子目录时把目录本身当作候选); 添加/编辑会校验路径存在、是文件夹、可读取, 并拒绝盘符根目录与用户主目录, 重复目录直接拦下。
- 路径缺失、不是文件夹、不可读或属于高风险位置时给出明确状态(候选显示为不可导入); 游戏被卸载后再次扫描会刷新该状态, 而用户的"已忽略/已导入"决定不会被覆盖; 与游戏库同名的候选会自动标记为"已导入"。
- 单个来源出错(注册表不可读、清单损坏)只影响该来源: 探测异常写入日志并在摘要里计数, 结果摘要(参与扫描的监控目录数、新增/更新数量、不可用路径数)显示在窗口底部, 手动添加游戏与存档位置始终可用。

### 质量门禁（与 pre-commit 及 CI 一致）：

安装 pre-commit 后，提交钩子只对本次变动的 Python 文件执行 Ruff、Black 和 mypy，pytest 只运行最高严重等级的 `tests/unit`。

```shell
uv run ruff check .
uv run black --check .
uv run mypy
uv run pytest --cov
```

每个测试用例都有最长执行时间(`pyproject.toml` 中的 `--timeout=60 --timeout-method=thread`)：卡住的用例会被计时器打断并打印所有线程的堆栈，而不是让整套测试一直等下去。个别确实较慢的用例可用 `@pytest.mark.timeout(120)` 单独放宽。

GitHub Actions 会运行全部测试，并生成覆盖率报告和 Allure 报告。手动生成 Allure 结果可使用：

```shell
uv run pytest --alluredir=allure-results --clean-alluredir
npx --yes allure@3 generate allure-results --output allure-report
allure open
```

每个用例都带四层 Allure 标签：标签由 `tests/conftest.py` 统一写入，测试模块用模块级 `pytestmark` 声明默认值，单个用例可用同名标记覆盖（如 `@pytest.mark.story("删除分支")`）；有未声明取值的用例按目录推断层次并在报告里归入“未分类”，`epic`/`layer` 拼错会在收集期直接报错。

| 标签              | 含义                                     | 示例                             |
| ----------------- | ---------------------------------------- | -------------------------------- |
| `@allure.epic`    | 产品级模块（闭集，见 `conftest._EPICS`） | 备份与分支 / 界面框架            |
| `@allure.feature` | 功能模块（与生产模块一一对应）           | 快照服务 / 数据仓储 / 主题调色板 |
| `@allure.story`   | 具体用户场景                             | 删除备份节点 / 深浅色主题切换    |
| `layer`           | 测试层次                                 | unit / integration / e2e         |

`epic`/`feature`/`story` 驱动报告中的“按产品级模块/功能/场景的稳定性分布”；`layer` 只能通过 `allure.dynamic.label("layer", ...)` 写入（`allure-pytest` 没有 `allure.layer` 装饰器），用于“按层耗时直方图”，同时写入 `parentSuite/suite/subSuite` 作为兼容。

稳定性分布控件需要至少 5 次历史运行的数据，CI 通过 `.allure/history.jsonl` 累积。本地想看到填充效果可复用同一套配置（注意每次都要先删掉输出目录，否则 Allure 不会覆盖已有报告）：

```shell
New-Item -ItemType Directory -Force .allure | Out-Null
Set-Content .allure/allurerc.json '{"historyPath": "./.allure/history.jsonl", "appendHistory": true, "historyLimit": 40}'
allure generate allure-results --output allure-report --config ./.allure/allurerc.json
```

### 构建 Windows 测试包

当前自动构建方案暂定为：当 `dev` 或 `bugfix/**` 分支的 Pull Request 合并到 `master` 后触发。也可以在 GitHub Actions 中手动指定分支或提交运行构建：

```shell
uv run pyinstaller --noconfirm --clean packaging/archive-management.spec
```

构建流程会直接读取 `packaging.py` 中的源码版本。每次构建会上传 Windows x64 的 onedir 压缩包、onefile 可执行文件、SHA-256 校验文件和构建元数据，供测试和验收使用。

正式 GitHub Release 的触发条件和版本生成方案尚未确定，当前不会由该流程自动创建 Release。稳定方案可以是提交时手动维护源码版本，或由 CI 生成不写回源码的构建版本，待发布策略确定后再启用。
