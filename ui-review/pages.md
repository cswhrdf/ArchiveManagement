# 界面逐页评审

截图来自 `ui-review/capture.py`（一次性脚本，不改产品代码）：

```powershell
uv run python ui-review/capture.py empty      # 空库: 临时 root, 拍 01~04
uv run python ui-review/capture.py populated  # 有数据: dev-data 的副本, 拍 05~29
```

- **空库**一遍是全新临时目录（真的什么都没有），**有数据**一遍是 `dev-data` 整份复制到
  `ui-review/.tmp-dev-data/` 后跑的 —— 界面会把筛选/展示偏好写回 `home_state`，直接在
  `dev-data` 上跑等于改本地开发数据。脚本同时把联网补译名/补封面关掉了。
- 所有图都是**按窗口句柄**抓的（`tests/crash_capture.py` 同一套 `ImageGrab.grab(window=hwnd)`），
  被别的窗口盖住也不影响。
- **截图局限（影响下面若干条判断）**：按句柄抓只得到窗口**客户区**，看不到系统标题栏与窗口
  边框，所以"标题栏文案/图标/最大化按钮"这一项本轮没有评审；另外画面里看不出鼠标悬停态与
  动画过渡，悬停配色只能靠代码/历史判断。
- **两处状态是脚本注入的**：`11/12` 的启停表格（真实轮询要有游戏进程在跑才会出队列内容）、
  `17` 的快捷键录制中（真实录制要按住按键）。其余画面都是应用自己读出来的真实数据。
- **改前基线**：`ui-review/screens-i3-before/`（2026-09-30 17:19 拍的同一套 29 张，I-3 中文标点
  全角化之前）。要比对"文案改动前后"时拿它做左图，不要拿 `screens-before/`（那是 09-26 的上一轮
  版式基线）。`screens/focus-ring/` 那 8 张焦点环放大图是 09-28 的，只含"确认/取消"两个词，
  不受标点改动影响，本轮沿用未重拍。

## 空库（01~04）

### 01-主页-海报视图-空库.png

- **位置**：主窗口 → 游戏主页 → 游戏库分区 → 海报展示（0 款游戏）
- **能做什么**：切列表/海报、切视图页签与筛选、批量导出、走右上角「+ 添加游戏」或「导入归档包…」，也可以切到「游戏发现」扫本机已安装的游戏。
- **看起来不对劲**：
  1. 空状态下右侧仍常驻一条**竖直滚动条**，而且拖不动 —— 视觉上在说"下面还有内容"。
  2. 空状态只有左上角两行小字（"游戏库还是空的。" + 一行提示），却占着约 1300×520 的深色卡片，密度低到像渲染失败；海报模式下尤其明显（连海报卡片的轮廓都没有）。

  4. 顶栏「+ 添加游戏」是全站唯一的高亮绿按钮，与"打开详情"选中态、页签选中态同色系 —— 一个代表"主操作"、两个代表"当前状态"，语义混在一起。

### 13b-游戏详情-分支图-收起子树.png

- **位置**：同 13，另外把一棵子树收起来了（点框右下角的 `-` 标记，或选中后按空格）
- **能做什么**：同 13；折叠只是把画面收拢，选中项、右侧面板与工具栏按钮一律不变；再点一次标记（或选中后按空格/回车）就放回去。
- **本轮（I-9.5）新增的看头**：
  1. 收起后的框右下角变成 `+`，说明行从“时间 · 类型”换成 `N 个后代` —— 藏了多少必须写在框上。

## 已修（本轮的两处文案/排版缺陷，2026-10-01）

两处都在 `track_wraplength`（`ui/widgets.py`）上收口：它以前**只看容器宽度**，现在改成

- **上限不越过标签自己分到的宽度**：取 `min(容器宽 − inset, 标签现在的宽)` —— 修②（监控目录页
  那条说明从 1122 收到 928，整句改成两行、尾句回来了）；
- **判定延后到 idle、同一轮只算一次**：而它踩过的两个坑都在注释里：
  1. `CTkLabel.bind` 会把回调**同时**挂到内层 `tkinter.Label` 上，而那个控件的宽度就是**文字宽度**
     （由 wraplength 反推） —— 拿它当上限会把说明越排越窄（实测 27 号对话框里从 468 一路掉到
     下限 240）；
  2. 绑在**顶层窗口**上时，Tk 会把所有子控件的 `<Configure>` 也送进这个绑定（子控件 bindtags 里
     带着顶层窗口路径），宽度是那个子控件的（实测 24/33/100）。

①（`27` 的孤行）走的是另一条路：`dialogs._dialog_hint` 不再写死 `wraplength=460`，改成
`fill="x"` + `track_wraplength(window, label, inset=2×24)`。

**量出来的效果（修后）**：

| 对话框                          | 说明文字          | 修前                                  | 修后                              |

| `27-批量导出` 筛选说明（44 字） | 需要 470          | `wraplength=460` → 末尾 `。` 独占一行 | `470`（自己 470）→ **一行放得下** |
| `29-批量导入` 逐款说明（41 字） | 需要 451          | 同样按 460 断                         | `485`（自己 485）→ 一行           |
| `10` 监控目录说明               | 需要 1020（单行） | `1122` → 尾部硬裁                     | `928`（自己 928）→ 两行、完整     |

**踩到的死循环（教训，已写进注释）**：第一版让判定同时跟“容器”与“标签自己”，结果对
"内容撑高的容器 + 按需滚动条"（空库主页的空状态说明、发现页空卡片的说明）成了一个
**240 ↔ 252 的死循环**：说明宽 12px 就多一行 → 滚动条出现 → 宽度变回去 → 再写…… 实测 3 秒里

## 第二轮复核（`wraplength` 跟着格子走 + macOS CI 的两条红，2026-10-01）

## I-7 的"进行中 / 取消 / 结束 / 失败"四种反馈状态（2026-10-01，收尾）

I-7 验收里有一条"逐动作走一遍并截图"，一直缺的正是**进行中**那张 —— 原因很实在：
`DemoArchiveService.task_status()` 恒返回 `running=False`，而真后端（SQL）只在它自己的 `_active`
存在时才报"进行中"，**而"把耗时拉长"只能拉在它开始之前**（实测拉到 6s 依旧 `cancellable=False`）。
所以截图脚本新增了 `feedback` 模式：状态由脚本给，渲染仍是产品自己的逻辑；失败那张走产品自己的
`_report_read_failure`。命令与产物：

```powershell
uv run python ui-review/capture.py feedback   # 产物在 ui-review/screens-feedback/（5 张）
```

脚本会把每张照片对应的**文字证据**打到日志里（评审不用靠猜图），实测：

| 图                     | 任务卡                                             | 状态栏                                                                       |
| ---------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| `f1` 进行中            | `运行中` + 进度条                                  | `… 正在创建「测试游戏」的备份…`                                              |
| `f1b` 进行中（滚到底） | `运行中` + 进度条 + **`35%`** + **可点的「取消」** | 同上                                                                         |
| `f2` 取消已请求        | `运行中`                                           | `… 正在取消备份…`                                                            |
| `f3` 取消完成          | `已暂停`（取消入口收起并置灰）                     | `已取消备份，未写入任何备份节点`                                             |
| `f4` 失败              | `已暂停`                                           | `✕ 读取数据失败：unable to open database file；请重试，仍然失败时请查看日志` |

**两条复核结论**：

1. **验收要的三件事都在**：进行中可辨识（`运行中` + 进度行 + 具体在动哪一个）、可取消（「取消」可点，
   点下去立刻有 `… 正在取消备份…` 的回执）、结束后说清结果与去处（`已取消备份，未写入任何备份节点`
   = 发生了什么 + 没动数据）；失败文案带"接下来怎么办"（`请重试，仍然失败时请查看日志`）。
2. **一条新发现（未修，已登记进 I-7 的开放项）**：默认窗口 1360×860 下，任务卡的**第三行**
   （进度文案 + 取消按钮）在侧栏折叠线以下 —— 只有滚一下才看得到，所以进行中现场（`f1`）只露出
   前两行。侧栏可滚，所以不是"点不到"，但"跑着的时候取消按钮不在视野里"确实削弱了 I-7 想要的
   "可取消"。`f1b` 就是滚到底拍的对照。

**新守卫**（咬合验证过）：`tests/integration/test_gui_states.py::test_busy_task_card_is_recognizable_and_cancelable`
—— 判据 E：用只报 `running/cancellable` 的替身后端走一遍真实流程（`_on_backup`），断言「运行中」+
进度行 + 进度文案 + 取消按钮可用 + 长操作入口置灰；点取消要真的传到后端（`cancel_active` 被调用）、
立刻有"正在取消"的回执；收尾必须是 INFO 的"已取消"（**取消不是错误**），并让取消入口跟着收起。
咬合验证：把 `_render_task` 里那个 `cancellable` 判断掐掉 → 红（`进行中却没有可用的取消按钮`）。
