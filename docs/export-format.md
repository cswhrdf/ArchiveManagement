# 导出包格式参考

导出包是软件写出的归档文件（后缀 `.archive.zip`，文件名由界面里的保存对话框决定）：把这台机器上的一款或几款游戏、连同它们的全部备份内容装进一个文件，便于搬到另一台机器或长期留档。

本文说明包的目录结构、清单与配置字段、各项上限与读写纪律。**取值的权威定义在
`src/archive_management/services/export_format.py`**（`EXPORT_FORMAT`、`EXPORT_FORMAT_VERSION`、
`PACKAGE_KIND`、`BATCH_KIND`、`MAX_*`、`_KIND_LABELS` 等常量）：本文只解释含义与当前取值，
改代码时不必同步改本文；两者不一致时**以代码为准** —— 这份文档刻意不做第二个事实来源。
用户视角的操作说明见 [features.md](features.md) 的「导入与导出」。

## 两类包

| 类型     | 清单里的 `kind` | 用途                                  |
| -------- | --------------- | ------------------------------------- |
| 单游戏包 | `package`       | 导出选中游戏（详情页「导出游戏」）    |
| 批量包   | `batch`         | 一次导出多款游戏（主页「批量导出…」） |

两类包靠清单里的 `kind` 区分。**旧包（清单里没有 `kind`）一律按单游戏包读取**；拿错类型时
读取方报「包类型不符: 需要…, 实际是…」，不会等更深一层才失败。

### 单游戏包的文件树

```
manifest.json            # 清单: 格式版本、工具版本、游戏标识与逐条校验
config.json              # 配置: 游戏、存档位置、备份节点结构、定时任务
branches/<节点>/…        # 分支树上的每个备份节点(目录内含该节点自己的 snapshot.json)
timeline/<节点>/…        # 时间线上的恢复前安全点
```

节点内容按 `is_safety` 分放两处：普通备份与分支进 `branches/`，恢复前安全点进 `timeline/`。
每个节点的目录**原样搬过去**（含它自己的 `snapshot.json`，因此 `loc-<序号>` 原本对应哪条路径、
哪些条目是符号链接都能还原）。

### 批量包的文件树

```
manifest.json            # 外层清单: kind=batch + games[] 逐游戏一行
<slug>.archive.zip       # 每款游戏一个"单游戏包", 原样搬进外层 zip
<slug>-2.archive.zip     # 条目名撞车时追加 -2/-3…(比较忽略大小写)
```

批量包**没有 `config.json`**（配置属于各个内层单包），但内层内容不会被重复打包一遍：
外层只装**已经写好的单游戏包**，体积约等于各内层包之和。内层条目名由游戏名派生
（`game_slug(名称) + .archive.zip`）。

## manifest.json（单游戏包）

| 字段           | 类型   | 含义                                                                                              |
| -------------- | ------ | ------------------------------------------------------------------------------------------------- |
| `format`       | 字符串 | 固定标识 `archive-management.export`；不是这个值就是「这不是本工具的导出包」                      |
| `kind`         | 字符串 | 包类型，单游戏包为 `package`                                                                      |
| `version`      | 整数   | 包格式版本（当前 `1`）；读取方**只认这一个值**，未知版本直接拒绝，不猜结构                        |
| `created_at`   | 字符串 | 导出时间，UTC、ISO 8601（精确到秒）                                                               |
| `tool_version` | 字符串 | 写出这个包的软件版本                                                                              |
| `game`         | 对象   | 游戏标识（见下表），不含路径与用户数据                                                            |
| `files`        | 对象   | `{"count": 内容文件数, "bytes": 内容展开字节数}`，不含 `manifest.json` 与 `config.json` 自身      |
| `entries`      | 数组   | 逐条声明 `{"path", "size", "sha256"}`；`path` 是包内相对路径（正斜杠），`sha256` 是 64 位十六进制 |

`game` 对象：

| 字段            | 类型        | 含义                                                                    |
| --------------- | ----------- | ----------------------------------------------------------------------- |
| `name`          | 字符串      | 游戏名称（界面显示用）                                                  |
| `original_name` | 字符串      | 录入时的原始名称（用户改名不改写它）                                    |
| `steam_app_id`  | 整数或 null | Steam AppID；导入时用来找「疑似同一款」                                 |
| `platform`      | 字符串      | 运行平台标识：`windows` / `macos` / `linux`                             |
| `origin`        | 字符串      | 商店来源：`steam` / `epic` / `gog` / `ubisoft` / `monitored` / `manual` |
| `archived`      | 布尔        | 导出时该游戏是否处于归档状态                                            |

## config.json（单游戏包）

| 字段        | 类型        | 含义                                                                 |
| ----------- | ----------- | -------------------------------------------------------------------- |
| `version`   | 整数        | 与清单同版本号（当前 `1`）                                           |
| `game`      | 对象        | 清单里的 `game` 再加 `tags` / `enabled` / `machine_local`            |
| `locations` | 数组        | 存档位置，按 `loc-<序号>` 的顺序；序号与快照清单里的来源目录一一对应 |
| `backups`   | 数组        | 备份节点（分支、自动备份与安全点混排，用 `is_safety` 区分）          |
| `schedule`  | 对象或 null | 定时任务配置，没有配置就是 `null`                                    |

`game` 上的三个附加字段：

| 字段            | 类型       | 含义                                                                                                                                   |
| --------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `tags`          | 字符串数组 | 游戏标签                                                                                                                               |
| `enabled`       | 布尔       | 导出时是否启用。**这是本机状态**（全局至多一款启用），导入侧一律新建为停用、不照搬这个值（否则会出现两款同时启用），记下来只是如实留痕 |
| `machine_local` | 布尔       | 恒为 `true`：明确标记「这个启用态是本机的」                                                                                            |

`locations` 的每一条：

| 字段               | 类型   | 含义                                                           |
| ------------------ | ------ | -------------------------------------------------------------- |
| `index`            | 整数   | 位置序号，与 `branches/…`、`timeline/…` 下的 `loc-<序号>` 对应 |
| `path`             | 字符串 | 导出那台机器上的绝对路径                                       |
| `path_kind`        | 字符串 | `directory` 或 `file`                                          |
| `source`           | 字符串 | 位置来源，当前只有 `steam` 或 `manual`                         |
| `is_primary`       | 布尔   | 是否主位置                                                     |
| `original_machine` | 布尔   | 恒为 `true`：这条路径属于导出那台机器                          |

`backups` 的每一条：

| 字段             | 类型          | 含义                                                               |
| ---------------- | ------------- | ------------------------------------------------------------------ |
| `id`             | 字符串        | 包内节点标识 = 快照目录名（见下文「节点标识」）                    |
| `parent_id`      | 字符串或 null | 父节点的 `id`；根节点为 `null`                                     |
| `kind`           | 字符串        | 节点类型：`manual` / `branch` / `auto`（未知取值按 `manual` 处理） |
| `title` / `note` | 字符串        | 备份名称与描述                                                     |
| `branch_name`    | 字符串或 null | 分支名                                                             |
| `is_safety`      | 布尔          | 是否恢复前安全点（决定内容放在 `timeline/` 还是 `branches/`）      |
| `created_at`     | 字符串或 null | 节点创建时间（ISO 8601）；读不出来时留空，由数据库补当前时间       |
| `content_hash`   | 字符串或 null | 内容哈希，用于「内容没变不重复备份」的比对                         |
| `current`        | 布尔          | 导出时它是否是游戏的「当前节点」                                   |

`schedule` 的字段：`interval`（周期文本，如 `30m`）、`enabled`（布尔）、`keep_auto`（自动备份保留份数）。
导入侧的规则是**只在目标游戏本机还没有定时任务时才补上**（已有的不动，免得覆盖本机配置）；
周期文本为空就跳过。

## manifest.json（批量包外层）

| 字段           | 类型   | 含义                                         |
| -------------- | ------ | -------------------------------------------- |
| `format`       | 字符串 | 同上                                         |
| `kind`         | 字符串 | `batch`                                      |
| `version`      | 整数   | 同上                                         |
| `created_at`   | 字符串 | 同上                                         |
| `tool_version` | 字符串 | 同上                                         |
| `games`        | 数组   | 逐游戏一行（见下表），顺序与导出时的顺序一致 |
| `files`        | 对象   | 外层条目数与字节数（条目数等于游戏数）       |

`games` 里的每一行：

| 字段              | 类型        | 含义                                                 |
| ----------------- | ----------- | ---------------------------------------------------- |
| `entry`           | 字符串      | 内层包在外层 zip 里的条目名（单段、`.zip` 结尾）     |
| `name`            | 字符串      | 游戏名称（取自内层包清单；读取时会与内层包逐字比对） |
| `steam_app_id`    | 整数或 null | 同上                                                 |
| `platform`        | 字符串      | 同上                                                 |
| `nodes`           | 整数        | 备份节点数（内层包 `config.json` 的 `backups` 长度） |
| `files` / `bytes` | 整数        | 内层包的内容文件数与展开字节数                       |
| `size`            | 整数        | **内层包自身**的字节数                               |
| `sha256`          | 字符串      | **内层包自身**的 sha256（要求校验哈希时用它复核）    |

## 节点标识：为什么是快照目录名

包内节点 `id` 直接取**快照目录名**（数据库里 `storage_relpath` 的最后一段，形如
`<UTC 时间戳>-<8 位随机>`）：它在磁盘上天然唯一且稳定，换一台机器也不会撞车，所以包内
不需要再发明一套编号。`parent_id` 引用的是同一个标识，分支关系因此在包内自洽。

**刻意不导出**：

- **数据库行 id**：本机自增主键，换一台机器后没有意义（导入时按包内顺序重新落库）；
- **`games.storage_key`**（备份根下的游戏目录名）：它在本机首次备份时才确定、之后固定不动，
  且由「当时的游戏名 + 全部存档路径」推导 —— 这个前提在导入机器上完全不同（存档位置要
  用户重新映射）。导入时按映射后的路径重新推导（批量导入还会给同名同路径的游戏加一个由
  条目名派生的短后缀，让它们各占一个目录）；
- 封面/图标缓存、译名缓存、探测结果等**可再生数据**。

## 存档位置：路径来自导出那台机器

- 包内每条存档位置都带 `original_machine: true`，游戏上带 `machine_local: true`：明确标记
  「这条路径/这个启用态是本机的」。
- 读取方**不把包内路径当作可用路径**：体检时只探测本机有没有同名路径，导入对话框里每条
  位置给一行输入框，**本机已存在的才预填**；留空或删掉的那一条不导入，也不会新建存档位置。
- 映射进去的路径仍走既有的「新增存档位置」用例：规范化 → 判重 → 可访问性；不可用
  （不存在、类型不符、不可读）直接报错。
- 需要说明的是：`original_machine` 目前只是给人与其它工具看的标记，**读包时并不依赖它** ——
  导入一律按「路径来自导出机器」处理，逐条让用户确认映射。

## 上限

| 上限                 | 当前取值                              | 常量                                          | 为什么                                                         |
| -------------------- | ------------------------------------- | --------------------------------------------- | -------------------------------------------------------------- |
| 包内条目数           | 20 000                                | `MAX_ENTRIES`                                 | 正常游戏存档远小于这个数量；条目数爆炸会拖垮解包与列表         |
| 单个文件             | 4 GiB                                 | `MAX_ENTRY_BYTES`                             | 正常存档不会有这么大的单个文件                                 |
| 展开后总大小         | 24 GiB                                | `MAX_TOTAL_BYTES`                             | 防「解压炸弹」：一个包的落盘量必须有上限                       |
| 单条目压缩比         | 2000.0（压缩后小于 1 KiB 的条目不判） | `MAX_COMPRESSION_RATIO`、`_RATIO_FLOOR_BYTES` | 几千倍的比率只出现在刻意构造的包里；小文件的比率没有意义       |
| 批量包里的游戏数     | 500                                   | `MAX_BATCH_GAMES`                             | 一次导入几百款在界面上已经没有可用性，也远超「自己的一批游戏」 |
| 批量包里的游戏数下限 | 1                                     | —                                             | 空批量包没有意义，写包与读包都拒绝                             |

上限在**写包与读包两侧都查**：写侧在打包前对来源文件逐个取大小与哈希；读侧先按 zip 目录里
的声明查一遍，再在真正解出时按实际读到的字节数复核一次（免得 zip 头里的声明与实际内容不符）。

## 写入纪律

单游戏包（`write_package`）：

1. 规划条目：按包内路径排序 → 拒绝符号链接来源、非普通文件、超过单文件上限的条目 →
   检查总量与条数上限 → 拒绝重复路径；
2. 目标**同级**的临时文件 `<目标文件名>.partial-<8 位随机>`（必须同盘，改名才是原子的）；
3. 写入：先 `config.json`，再按路径顺序分块写入各内容文件，最后写 `manifest.json`；
4. **回读校验**：重新打开包，条目集合必须与清单一致，逐条比对大小与 sha256
   （只信任磁盘上真正写出来的字节）；
5. 全部通过才原子改名为目标文件；任何一步失败都会删掉临时文件。

批量包（`write_batch_package`）：各内层单包先落在目标同级的暂存目录 `.batch-<8 位随机>/`
里（**不在备份根下动任何东西**），全部成功后才按上面同一套纪律写外层包，最后删掉暂存目录。
**任何一款失败或取消都让整批失败**，目标路径上不留文件 —— 静默少导一款会让用户以为这一批
都归档好了。

同名文件：导出到用户选定的路径时，若该文件名已存在会被**原子替换**（保存对话框里用户已经
确认过这个名字）。这与导入侧「永不覆盖」是两条不同的规则。

## 读取与解出纪律

读包（`read_package`、`read_batch_package`，全部在**写出任何文件之前**完成）：

文件存在 → 是合法 zip → 清单与配置是可解析的 JSON 对象 → 格式标识/版本/包类型 → 上限 →
每个条目的路径安全且不重复 → 清单声明与实际条目一一对应 →（可选）逐条哈希比对。
**体检阶段不校验内容哈希**（只解析结构，快）：单游戏包只读清单与配置；批量包会把内层包
解到系统临时目录（`BatchContents` 退出时删除），但同样不比对哈希。

真正导入时两条路径走**同一条校验纪律**：

- **单游戏包**：`import_package` 先 `read_package(..., verify_hashes=True)` 把包内每个条目
  与清单逐条复核一遍，再解出；
- **批量包**：`import_batch` 同样以 `read_batch_package(path, verify_hashes=True)` 读包，
  **外层清单里每个内层包的 `sha256` 也会逐条复核**（体检为了快可以不校验，但真正落库之前
  必须核对过，否则「只落已校验的内容」这条就不成立）。每个内层包再由单包读包逻辑完成各自的
  全部校验（结构、上限、压缩比、符号链接与「清单声明 ↔ 实际条目」对应关系）；解出节点内容时
  `extract_package` 同样默认逐条比对哈希。

解出（`extract_package`）：每个条目先解析成目标目录下的路径（`member_target` + `is_within` 兜底）→
目标已存在同名文件就**拒绝覆盖** → 边写边算哈希 → 按实际字节数复核单文件与总量上限 →
大小必须与清单一致 →（可选）哈希一致 → 失败时删掉这个半成品文件。

批量包：外层只做「结构 + 上限 + 条目名」这一层检查；每个内层条目解到临时目录后交给单包读包
逻辑走**全部**校验，因此批量格式没有第二套单包校验。内层包还要与外层清单那一行比对游戏标识
（`name` / `steam_app_id` / `platform` 必须一致）—— 这是「内层包装的是另一款游戏」的唯一拦截点。
解出来的内层包存放在临时目录里，生命周期由 `BatchContents` 上下文管理器负责（退出时删除）。

## 读取方拒绝的输入

单游戏包：

- 文件不存在，或不是合法 zip（压缩包损坏）；
- 缺少 `manifest.json` / `config.json`，或它们不是 JSON 对象；
- `format` 不是 `archive-management.export`，或 `version` 是未知版本；
- 包类型不是单游戏包（给了批量包）；
- 条目数、单个文件、展开总量或压缩比超过上限；
- 包内路径不是安全相对路径（绝对路径、盘符、反斜杠、`.`、`..`、空段、以 `/` 结尾）；
- 含有**符号链接条目**（包是外部输入，不跟随链接才能保证只在目标目录里写普通文件）；
- 同一路径出现多次（清单里重复，或 zip 里重复）；
- 清单声明与实际条目对不上（缺条或多条）；
- 清单条目的 `size` / `sha256` 形态非法；
- 校验哈希时发现内容与清单不一致。

批量包：

- 上面这些外层形态（清单缺失、类型不符、条目名非法、缺条多条、条目大小不符）；
- 清单里没有游戏，或游戏数超过上限；
- 清单里同一个 `entry` 出现两次；
- 内层条目名不是单段 `.zip` 文件名（含 `/`、不以 `.zip` 结尾）；
- 某个内层包不是合法的单游戏包（报错会带上条目名，所以坏包也能报出是哪一款）；
- 外层清单那一行与内层包的游戏名称、AppID 或平台不一致。

## 导入时的冲突处理

| 策略           | 键      | 行为                                                                                                               |
| -------------- | ------- | ------------------------------------------------------------------------------------------------------------------ |
| 新建游戏       | `new`   | 新建一条游戏记录（**默认停用**，由用户自己启用一款），再导入备份节点与已映射的存档位置                             |
| 合并到现有游戏 | `merge` | 备份节点追加到目标游戏的分支树上：根节点的父节点是该游戏在数据库里的**当前节点**；目标必须明确选定，未选时直接报错 |
| 跳过           | `skip`  | 什么都不写，只回报跳过了多少份备份                                                                                 |

三条同时成立的规则：

- **永不覆盖**：目标位置已存在同名节点目录时**跳过该节点并计数**（重复导入同一个包不会产生
  重复数据）；存档位置走既有的判重（规范化 + 同一目录只登记一条）。
- **同名允许**：包里的游戏名与库里某款相同时不阻止新建；同一个批量包里两款同名同路径的游戏
  也会各占一个备份目录（由条目名派生的短后缀区分）。
- **失败边界是「一款游戏」**：导入某一款时中途失败只回收它本次已落位的备份节点（目录 + 数据库行）；
  它新建的游戏记录与已经写入的存档位置保留，之前导完的游戏也原样保留。批量导入失败会让**整批停下**
  （不继续导后面的，已导完的保留），用户修好后重跑时已存在的节点会被跳过。

用户视角的操作说明（在哪导出、对话框怎么选、报什么提示）见 [features.md](features.md) 的「导入与导出」。
