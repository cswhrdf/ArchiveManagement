# 视觉回归基线图

这里的 PNG 是 `scripts/create_allure_visual.py` 的比对基准(CI 的质量作业每一轮都读它)。
判据是感知哈希距离 + SSIM,阈值写在那个脚本的模块常量里。

## 拍的是哪七张

编号不只是文件名的一部分:**报告里的列表顺序就是它**。脚本按文件名的字母序处理(所以编号要
接在末尾), 每张结果的开始时间由"基准 + 序号"给出 —— 少了后半句会出现"相邻两张时间戳相同、
报告里因此看不出先后"的情况(2026-10-03 就是这样: 列表成了 `01, 03, 02, 05, 04, 06`)。所以
**新增画面要接在末尾编号**, 重排编号时这张表要一起改。

| 文件名                                | 拍的是什么                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------------- |
| `01-主页-列表视图-演示数据.png`       | 列表表格(列宽、名称裁剪、状态列、页脚计数)                                            |
| `02-主页-海报视图-演示数据.png`       | 海报网格(卡片尺寸/元信息/选中描边)                                                    |
| `03-详情页-演示数据.png`              | 详情页(表头、概要卡、备份列表)                                                        |
| `04-详情页-分支图折叠态-演示数据.png` | **收起一棵子树**之后的图: 右下角的标记、说明行里的 `N 个后代`、以及折叠没把别的框挤歪 |
| `05-主页-游戏发现-演示数据.png`       | 发现分区与候选列表                                                                    |
| `06-主页-游戏启停-演示数据.png`       | 启停分区的开关与监控列表                                                              |
| `07-主页-列表视图-空库.png`           | 一条数据都没有时的空状态(连表头一起收起来)                                            |

数据来自**演示后端**(`ui/demo_backend.py`): 模块级常量、不联网、不读 `dev-data`、不写盘,
所以每次跑出来完全一样 —— 但它**有游戏/有备份/有候选**, 于是上面那些真正的布局才被覆盖到
(早期只拍空库, 那些布局一个都没被看过)。

## 前提: 画面得先画得出汉字

每一步的结果里都挂着 `fonts.txt`, 内容是**字体探针**(平台 / Python / Tk 版本、`_tkinter`
模块与 Tcl/Tk 库的路径、选中与实际的字体族、汉字与拉丁的量宽、判定)。判定不通过时:

- 结论标红、退出码 2;
- **不产出候选基线** —— 宁可这一轮没有基线, 也不拿一张看不清的图当"正确"。

2026-10-02 就是这么踩的: 候选基线里整排按钮是空的(汉字一个都没画出来)、拉丁字形也是位图
字体(锯齿), 而那一轮在报告里是**通过**。根因是那一步用的 Tk(uv 托管的 CPython 自带
`libtcl9tk9.0.so`)在 X11 上只走**核心位图字体**(没有 fontconfig/FreeType, 看不到任何 TTF),
`fonts-noto-cjk` 装多少都没用。现在那一步只**换 Tk 不换解释器**: 解释器仍是 uv 托管的那份
(与其余作业同版本, 所以报告里"平台 / Python / Tk"那行是真的), `_tkinter` 换成发行版
`python3-tk` 的那一个(链发行版 libtk8.6, 走 Xft/fontconfig), 由 `ci.yml` 的 `PYTHONPATH`
与 `UV_PROJECT_ENVIRONMENT` 固定住。

## 为什么入库

视觉回归要回答的是"**这一版把界面改了吗**"。基线跟着代码走,改动才会出现在 PR 的 diff 里
—— 评审时能直接看到"这版把基线图也换了", 而不是让一条自动更新的基线悄悄把变化吃掉。

## 怎么采

CI 每轮都会把**本轮真实画面**作为 `visual-baselines-candidates` 产物上传(无论比对通过与否)。
需要新建或更新基线时:

1. 下载那一轮 CI 的 `visual-baselines-candidates` 产物;
2. 逐张看过, 确认画面是有意改的(不是被裁了、没换行、颜色错了);
3. 把图放进本目录,**文件名必须与产物里的一致**(即"页面-状态"那个名字);
4. 同一个 PR 里一起提交 —— 这样"界面变了"和"基线也变了"是同一件事。

## 为什么只在 Linux 采

字体度量是画面的一部分: 同一份代码在 Windows 与 Linux 上排出来的像素并不相同。基线只在
CI 的 Ubuntu 作业(经 `xvfb-run -s "-screen 0 1600x1000x24"`)上采, 也因此**不按平台展开**
—— 三个平台各采一套, 只会把"字体不同"变成一堆假红。

## 缺基线时会怎样

某张画面没有对应文件时, 脚本**不判失败**: 它把这一轮的画面写成候选基线, 并在报告里写明
"基线尚未入库"。这样第一轮不会永远卡住, 同时"没判据"也不会被混进"通过"。

## 会改画面的东西

画面是**像素级**比较, 所以下面这些都与基线绑在一起:

- 界面上出现的常量文案, 包括状态栏那行"全局快捷键不可用: ……"的原因(`create_allure_visual.py`
  里的 `WINDOW_TITLE` / `HOTKEY_UNAVAILABLE_REASON` —— 它们在界面里, 所以是具名常量);
- `CJK 字体`(CI 装的是 `fonts-noto-cjk`)与 `xvfb` 的屏幕尺寸/色深;
- 窗口尺寸(`WINDOW_SIZE`, 与产品默认一致)。

改这些就要重采基线; 阈值(距离 **2** / SSIM **0.995**, 见 `create_allure_visual.py`)是按 CI 上
**实测的分布**定的(2026-10-05): 同渲染噪声实测为 0(四张逐位相同: 哈希 0 / SSIM 1.0000),
而真实界面变化最小到 SSIM 0.9819、已知的真缺陷是 0.9722 —— 两类"真要人看一眼"的都仍判红。
**不要凭印象改**: 太紧会把 runner 镜像更新(字体/驱动变化)变成随机红(那时先确认"是新基线还是
阈值"), 太松等于没判据。
